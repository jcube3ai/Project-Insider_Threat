SOP — Introduction
How This Integration Works
Before starting, understand the architecture. The framework is designed to be deployed in phases — Tier 1 rules run independently on day one. Baselines and correlation add depth over time. The system runs entirely natively inside XSIAM. No external datasets, no HTTP collectors, no maintenance overhead. Our GitHub repo is the source of truth for the taxonomy — XSIAM is the execution layer.
Start in Dev. Complete all 6 steps and validate all 5 test scenarios before touching our production XSIAM tenant. The T6 correlation rule will create incidents — you need to confirm thresholds are correct first.
Step 1
Lookup Tables
hr_risk_context, business_context, itdf_correlation_output — the data T6 reads to make decisions
Step 2
Baseline Queries
Scheduled XQL that builds "what normal looks like" per user — required by 40+ of our 71 rules
Step 3
Alert Rules (3 to start)
Our individual XQL detections — each tags its alerts with itdf_technique, itdf_tactic, itdf_score
Step 4
T6 Correlation Rule
The T6 correlation engine — reads every xdr_alerts tagged itdf_detection, scores per user, applies risk multipliers, and creates incidents when thresholds are crossed. This is how the system filters false positives without baselines for Tier 1 rules.
Step 5
Playbook
Automated response — enriches, summarizes, notifies, sets SLA when an incident is created
Step 6
End-to-End Testing
5 test scenarios validate every layer — single signal, multi-signal, leaver multiplier, dampener, critical

Native XSIAM scheduled queries that build per-user behavioral baselines. These run entirely inside XSIAM — no external pipeline, no GitHub dependency. Baselines are NOT required for our Tier 1 rules (T4.1, T3.7, T5.1 have near-zero false positives without them). Baselines are optional for Tier 1 deployment. Deploy T4.1, T3.7 and T5.1 first — they have near-zero false positives without any baseline. Add baselines only once our Tier 1 rules are generating tagged alerts in xdr_alerts. These run natively inside XSIAM as scheduled queries — no external pipeline, no GitHub dependency, no maintenance overhead. Allow at least 5 days of data before trusting p95 thresholds. BASELINE 1 baseline_file_access Required for T1.1
30-day rolling p95 of daily file access per user. T1.1 fires when a user accesses more than 2× their personal p95 in a single day.
SettingValue
NameITDF Baseline — File Access
ScheduleDaily at 01:00 AM
Output tablebaseline_file_access
XQL baseline_file_access 
// ITDF Baseline — File Access | Daily 01:00 | Output → baseline_file_access

dataset = xdr_data
| filter event_type = ENUM.FILE
    and event_sub_type = ENUM.FILE_OPEN
    and _time > to_epoch(now() - duration(30d))
| bin _time span = 1d
| comp count() as daily_count
  by actor_effective_username, _time
| filter actor_effective_username != null
| filter not (actor_effective_username contains "NT AUTHORITY")
| filter not (actor_effective_username contains "SYSTEM")
| comp
    avg(daily_count) as avg_daily_files,
    approx_percentile(daily_count, 0.95) as p95_files,
    approx_percentile(daily_count, 0.99) as p99_files,
    count() as days_observed,
    max(_time) as last_updated
  by actor_effective_username
| filter days_observed >= 5
| fields actor_effective_username,
         avg_daily_files, p95_files, p99_files,
         days_observed, last_updated

04
Core Engine
Build the T6 Correlation Rule
One XQL rule that watches all ITDF-tagged alerts, aggregates scores per user, applies multipliers and dampeners, and creates XSIAM incidents when thresholds are crossed.
⏱ ~2 hours  |  XSIAM Incidents & Alerts → Correlation Rules → New Correlation Rule
This rule creates real XSIAM incidents. In dev this is fine. Before moving to production — validate all 5 test scenarios in Step 6 first. A misconfigured threshold will flood our incident queue.
HOW IT WORKS How T6 Filters Without a Baseline
This is the core of the native platform approach agreed with our team. Instead of building complex external baselines for every rule, T6 does the filtering through multi-signal correlation. A single alert from one rule rarely creates an incident. It takes multiple independent signals across different tactics before T6 escalates — making it self-filtering by design.
StepWhat happensHow
1Alert rule firesT4.1 detects log deletion — tags alert with itdf_technique:T4.1, itdf_score:4, itdf_detection
2T6 reads itT6 queries xdr_alerts hourly — filters on tags contains "itdf_detection"
3T6 scores the userSums itdf_score across all techniques fired for that user in the time window
4Multipliers appliedIf user is in hr_risk_context as leaver — score × 1.5 or × 2.0
5Threshold checkfinal_score ≥ 10 → ESCALATE  |  ≥ 15 → CRITICAL incident created
6Incident createdPlaybook triggers automatically — enriches, notifies, sets SLA
Why this replaces baselines for Tier 1 rules. A single T4.1 alert scores 4 — not enough to escalate on its own. But T4.1 (log deletion, score 4) + T3.7 (external forwarding rule, score 5) + T5.1 (privilege escalation, score 3) = 12 — that crosses the ESCALATE threshold. Three independent signals from three different tactics is a genuine insider threat pattern. No statistical baseline needed to make that determination.
When you DO need a baseline. Rules like T1.1 (bulk file access) fire on volume — "accessing lots of files" is meaningless without knowing what normal looks like for that user. That is when baseline_file_access is required. But T4.1, T3.7, T5.1 and the Azure AD techniques fire on specific behaviours that are suspicious in isolation — those never need a baseline.

XQL T6 Multi-Signal Correlation Engine — Full Query 
// ─────────────────────────────────────────────────────
// ITDF T6 — Multi-Signal Correlation Engine
// Runs every hour | Lookback: 24 hours
// Creates XSIAM incidents when ITDF threshold crossed
// Maps to: T6.1, T6.2, T6.3, T6.6 techniques
// ─────────────────────────────────────────────────────

// ── STAGE 1: Collect all ITDF-tagged alerts ────────────
// Only reads alerts tagged itdf_detection
// Ignores its own output to prevent feedback loops

dataset = xdr_alerts
| filter tags contains "itdf_detection"
    and _time > to_epoch(now() - duration(24h))
    and alert_source != "itdf_CORRELATION"

// ── STAGE 2: Aggregate by user ────────────────────────
// Sum scores, collect unique techniques and tactics

| comp
    raw_score            = sum(itdf_score),
    techniques_fired     = array_distinct(itdf_technique),
    tactics_fired        = array_distinct(itdf_tactic),
    alert_count          = count(),
    sum(
      if(high_confidence = true, 1, 0) as high_confidence_count
    ),
    first_signal         = min(_time),
    last_signal          = max(_time),
    alert_descriptions   = array_agg(itdf_description)
  by actor_effective_username

// ── STAGE 3: Multi-signal gate ────────────────────────
// T6.1 core rule: min 2 independent techniques required
// Prevents single noisy rule from dominating the score

| filter array_length(techniques_fired) >= 2

// ── STAGE 4: T0 precursor multiplier ─────────────────
// Leaver flag boosts the score significantly
// Source: hr_risk_context lookup table

| join type = left (
    dataset = hr_risk_context
    | fields username, is_leaver,
             days_to_departure, on_pip,
             role_changed
  ) as hr
  on actor_effective_username = hr.username

| alter precursor_multiplier = if(
    hr.is_leaver = true
      and hr.days_to_departure <= 14,  2.0,
    hr.is_leaver = true
      and hr.days_to_departure <= 30,  1.5,
    hr.is_leaver = true
      and hr.days_to_departure <= 60,  1.25,
    hr.on_pip    = true,               1.2,
    hr.role_changed = true,           1.1,
    1.0
  )

| alter adjusted_score = round(
    multiply(raw_score, precursor_multiplier), 1
  )

// ── STAGE 5: Business context validation (T6.3) ──────
// Legitimate explanations dampen the score
// Source: business_context lookup table

| join type = left (
    dataset = business_context
    | fields username, active_deal,
             approved_data_transfer,
             open_helpdesk_ticket,
             deal_name, ticket_number
  ) as ctx
  on actor_effective_username = ctx.username

| alter context_dampener = if(
    ctx.approved_data_transfer = true, 0.4,
    ctx.active_deal            = true, 0.6,
    ctx.open_helpdesk_ticket   = true, 0.8,
    1.0
  )

| alter final_score = round(
    multiply(adjusted_score, context_dampener), 1
  )

// ── STAGE 6: Escalation decision ─────────────────────

| alter escalation_level = if(
    final_score >= 15, "CRITICAL",
    final_score >= 10, "ESCALATE",
    final_score >= 5,  "INVESTIGATE",
    "WATCH"
  )

| filter escalation_level != "WATCH"

// ── STAGE 7: Build incident fields ───────────────────

| alter
    kill_chain_position = concat(
      "Tactics: ",
      array_to_string(tactics_fired, " → ")
    ),
    score_breakdown = concat(
      "Raw:",        to_string(raw_score),
      " × Precursor:", to_string(precursor_multiplier),
      " × Context:",   to_string(context_dampener),
      " = Final:",     to_string(final_score)
    ),
    leaver_note = if(
      hr.is_leaver = true,
      concat("⚠ LEAVER — ", to_string(hr.days_to_departure), " days remaining"),
      "Not a leaver"
    ),
    context_note = if(
      ctx.active_deal = true,
      concat("Active deal: ", ctx.deal_name),
      if(
        ctx.open_helpdesk_ticket = true,
        concat("Open ticket: ", ctx.ticket_number),
        "No business context found"
      )
    ),
    alert_source    = "itdf_CORRELATION",
    itdf_correlation = true

// ── STAGE 8: Final output ────────────────────────────

| fields
    actor_effective_username as subject,
    final_score, escalation_level,
    techniques_fired, tactics_fired,
    alert_count, high_confidence_count,
    kill_chain_position, score_breakdown,
    leaver_note, context_note,
    first_signal, last_signal,
    precursor_multiplier, context_dampener,
    raw_score,
    hr.is_leaver, hr.days_to_departure,
    ctx.active_deal, ctx.open_helpdesk_ticket

| sort desc final_score

TAGGING Rule Tagging Standard
Every ITDF alert rule must carry these tags in its XSIAM configuration. Inconsistent tagging breaks T6, the dashboard, and the attack chain. This is the single most important convention to protect — one wrong tag format means the entire downstream system misses that signal.
Non-negotiable. All 77 rules must use exactly this format. No abbreviations, no variations, no exceptions. If a rule fires without these tags T6 cannot see it and the attack chain will have gaps.
TagFormatExamplePurpose
itdf_detection Fixed string — no value itdf_detection Primary selector — T6 reads only alerts with this tag. Every ITDF rule must have it.
itdf_technique itdf_technique:{T}{tactic}.{sub} itdf_technique:T1.1 Maps the alert to its ITDF technique. Used by attack chain queries and dashboard heatmap.
itdf_tactic itdf_tactic:{T}{tactic} itdf_tactic:T1 Maps the alert to its tactic. Used by kill chain coverage and trend panels.
itdf_score itdf_score:{integer} itdf_score:2 Score weight. T6 reads this to calculate the user risk score. Must match the score defined in the framework.
XSIAM Where to Set Tags in XSIAM
In XSIAM, tags are set in the alert rule configuration — not in the XQL itself. Go to: Alert Rule → Settings → Tags. Enter each tag as a separate line.

itdf_score:2

PANEL 3 Risk Score Leaderboard
Top 10 users by aggregated ITDF score in the last 24 hours. Applies the leaver multiplier from hr_risk_context. Shows escalation level. This is the primary SOC triage view — the analyst opens the dashboard and immediately knows who needs attention. Build as a Table widget with conditional row colouring by escalation level.
XQL — Risk Score Leaderboard Widget type: Table | Refresh: every 15 minutes 
// ITDF Risk Score Leaderboard — top users by score
// Widget: Table | Refresh: every 15 minutes
// Applies leaver multiplier from hr_risk_context

dataset = xdr_alerts
| filter tags contains "itdf_detection"
    and _time > to_epoch(now() - duration(24h))

| comp
    sum(to_integer(itdf_score)) as raw_score,
    values(itdf_technique) as techniques_fired,
    count_distinct(itdf_tactic) as tactic_count,
    count() as total_alerts,
    min(_time) as first_signal,
    max(_time) as last_signal
  by actor_effective_username

// Join HR context for leaver multiplier
| join type = left (
    dataset = hr_risk_context
    | fields username, is_leaver, days_to_departure
  ) as hr
  hr.username = actor_effective_username

| alter multiplier = if(
    hr.is_leaver = true
      and hr.days_to_departure <= 14, 2.0,
    hr.is_leaver = true
      and hr.days_to_departure <= 30, 1.5,
    hr.is_leaver = true
      and hr.days_to_departure <= 60, 1.25,
    1.0
  )

| alter final_score = round(
    multiply(to_float(raw_score), multiplier), 1
  )

| alter escalation = if(
    final_score >= 15, "CRITICAL",
    final_score >= 10, "ESCALATE",
    final_score >= 5,  "INVESTIGATE",
    "WATCH"
  )

| filter escalation != "WATCH"

| sort desc final_score
| limit 10

| fields
    actor_effective_username as User,
    final_score as Score,
    escalation as Level,
    tactic_count as Tactics,
    total_alerts as Alerts,
    hr.is_leaver as Leaver,
    hr.days_to_departure as DaysLeft,
    techniques_fired as Techniques,
    first_signal as First,
    last_signal as Last
